# S0 交底 — 采集用户的业务地图

用户已经知道核心业务关系,这一步是把它从脑子里取出来变成可执行的靶心。**取得越准,后面越省力;取得含糊,后面全是空转。**

## 提问纪律

一次问全部会把人问烦。分两轮:

**第一轮:骨架(必问,不问清不往下走)**

1. 核心业务对象有哪些?(它们通常各自对应一张主表和一个状态)
2. 它们之间的数据流向?(A 产生 B?A 触发 B?A 是 B 的前置?)
3. 这次梳理的边界在哪?(从哪个动作开始,到哪个动作结束)
4. 这份文档给谁用?

第 4 问决定深度:新人 onboarding 只要主干 + 术语;要重构或替换系统,就得挖到业务规则和边界条件。**先定下来,否则容易做成一份没人看的百科全书。**

**第二轮:锚点线索(有多少要多少)**

对每个业务对象问:「它在代码/数据库里大概叫什么?」

用户往往能立刻说出表名或字段前缀——这是他们日常查数据用的,比任何猜测都准。拿不到也没关系,S1 可以从 recon 结果反推,但会多花一轮。

## 用户给不出结构化答案时

常见情况:用户能讲清业务,但讲的是叙事而不是列表。这时**不要追着要结构化输入**,而是听完之后自己整理成一张表,回读给用户确认:

> 我理解你说的核心对象是:批次、光罩订单、签核记录。流向是批次 → 签核 → 光罩订单。对吗?有没有漏掉的?

人对纠正比对填空配合度高得多。这个技巧在后面 S4 的缺口清单里还会再用一次。

## 锚点文件格式

整理成 `anchors.txt`,喂给 `probe.py --anchors`:

```
# 业务名 = 别名列表(表名 / 字段前缀 / 类名 / 拼音缩写)
批次 = TO_BATCH, BATCH_ID, batchNo, Batch, PC
光罩订单 = MASK_ORDER, MO_, MaskOrder, GZDD, guangzhao
DRC签核 = SIGNOFF, SIGN_OFF, DRC, signoffFlag, QH
GDS数据 = GDS, OASIS, GDS_VER, layout
```

**别名宁滥勿缺。** 命中噪音人工剔除很便宜,漏了则整条业务线断在这里而且不易察觉。每个对象尽量覆盖四类写法:

| 写法类型 | 例子 |
|---|---|
| 表名 / 表前缀 | `TO_BATCH`、`MASK_ORDER` |
| 字段名 / 字段前缀 | `BATCH_ID`、`MO_` |
| Java 类名 / 构件名 | `MaskOrderBiz`、`BatchDao` |
| 拼音缩写 | `GZDD`(光罩订单)、`QH`(签核) |

拼音缩写这一类特别重要:EOS 时代的国产系统里非常常见,而且是最容易漏的——因为它既不像英文单词也不像中文,搜索时想不起来。**主动向用户确认有没有拼音命名习惯。**

太短的别名(1~2 字符)会命中大量噪音,尽量避免;必须用时给它加上下文,比如用 `MO_` 而不是 `MO`。

## 业务地图的记录格式

存成 `_seed/business_map.md`,后续 S3 对账时逐条核对:

```markdown
## 核心业务对象
| 业务名 | 用户描述的职责 | 用户给的代码线索 |

## 用户断言的数据流向
| # | 从 | 到 | 关系性质(产生/触发/前置/引用) | 用户描述 |

## 梳理边界
- 起点:
- 终点:
- 明确排除:

## 文档受众与深度
```

给每条数据流编号(F1、F2……)。S3 的对账表按这些编号逐条核销,漏没漏一目了然。

## 这份地图的地位

它是**高置信假设**,优先于任何行业常识,但仍需代码印证(铁律三)。

在所有产物中,来自用户地图但代码尚未印证的内容标 `[U] user-asserted`。这个标记不是质疑用户,而是让后来的人知道哪些结论有代码兜底、哪些依赖于某个人当时的口述——半年后这个区别非常重要。
