# S4 — 合成与缺口

把 S0~S3 的产物拼成一份能给人读的流程文档,外加一份能拿去问人的清单。

## 硬性约束:不读代码

只用 `00_repo_map.md`、`01_objects.md`、`02_dataflow.md` 和 `business_map.md`。三个理由:

1. **上下文预算** —— 到这一步已消耗大量上下文,再翻代码会挤掉刚取证的结构化信息,合成质量断崖下跌
2. **强制证据链** —— 只能用已带证据的结论,新结论无处诞生,幻觉没有入口
3. **暴露缺口** —— 拼不出连贯流程说明前面漏了东西,这个信号很宝贵

拼不上就写「流程断裂,缺少 X」,**抵抗把断裂处补圆的冲动**。补出来的连接是纯编造,而且出现在成品显眼位置,危害远大于中间产物里的一条错误记录。

## 合成方法

以用户的业务地图为骨架(它已经是对的骨架,不要重新发明),把取证结果挂上去:

```
业务阶段(来自用户地图 + S2 状态机)
 ├─ 参与角色与操作入口   (S2)
 ├─ 前置条件与业务规则   (S2)
 ├─ 状态变化             (S2)
 ├─ 数据流入流出         (S3)
 └─ 产出的文件/记录      (S2)
```

每个阶段回答:**谁**做、做**什么**、必须满足**什么**、产生**什么**。

## 异常路径不能略过

正常路径通常好还原,但**遗留系统的真正复杂度在异常路径**:打回重提、ECO 变更回退、跨状态强制干预、超时自动处理、管理员后门。

这些恰恰是新人最需要知道、文档最容易漏的部分,也是用户在 S0 口述时最不会主动提的部分(因为不是日常主线)。S2 的「无前置约束的写入点」和 S3 的 C 类在这里兑现价值。

发现绕过正常流程的管理入口必须单独标出。

## 产物二:`04_open_questions.md`

**这份文件是主动工具,不是遗留物。** 它是整套沉淀里杠杆最高的产物。

用户已经知道业务,所以这里的问题不是"流程是什么",而是**代码里那些他不知道的东西**——S3 的 B、C、D 三类天然就是最好的问题素材。

### 问题写法:判断题,不是问答题

每个问题用「我们的发现 → 证据 → 存疑点 → 请确认」:

> **Q3. 光罩订单提交存在一条跳过签核校验的分支**
> 发现:`MaskOrderBiz.java:241` 有 `ADMIN_FORCE` 分支,走此分支时不校验 `SIGNOFF_FLAG`。
> 证据:`MaskOrderBiz.java:241`,入口在 `admin/forceSubmit.jsp:18`,可见性限 `SYS_ADMIN` 角色。
> **请确认:这个口子实际什么场景会用?谁在用?还需要保留吗?**

对比无效写法:「签核和光罩订单是什么关系?」——用户会答"就是要先签核啊",信息量为零,而且他早就在 S0 说过了。

### 分类与优先级

按**回答成本**排,最容易答的放前面:

- **A 类 · 一眼能答** —— 术语中文含义、外部系统 IP 对应哪个系统、字典值含义、孤儿状态是不是废弃。集中成一张表让人一次填完
- **B 类 · 需要回忆但清楚** —— 某规则的业务原因、某绕过口子的使用场景、某顺序为什么这样
- **C 类 · 需查证/跨部门** —— 上下游对接约定、历史分支是否还在用
- **D 类 · 静态分析答不了** —— 哪些路径实际已废弃、各分支使用频次。明确标注「需要日志或埋点」,说明这不是遗漏而是方法论边界

### 高杠杆问题

同一个底层未知常在多处冒头(一个不明构件同时导致术语未知、流转不明、边界不清)。**合并成一个问题,并注明解开后能同时消除哪几处不确定**,排在最前面单独标出。

## 产物三:`README.md`

最后写,是给人的入口:

1. 覆盖了什么、**没覆盖什么**(scope 边界写死)
2. 各文件导读:新人按什么顺序读
3. 置信度总览与主要盲区
4. 维护约定:改代码时怎么同步改文档;建议这套文档放进代码仓库,与代码同一次提交
5. 生成方式:用了什么 skill、基于哪次快照、怎么增量重跑

## 收尾时告知用户

- **先看 `02_dataflow.md` 的 C 类**——那是他最可能不知道的部分,也是这次梳理的主要增量
- B 类冲突需要他判断是代码 bug 还是认知偏差,skill 不做这个判断
- 确认后的答案要**回填到对应产物并更新置信度**,而不是只留在 04 里。文档要能收敛,否则下次梳理又要从头再来
- 死代码判断、真实数据追踪需要运行时数据和生产库权限,不在本 skill 范围
