# S3 — 数据流对账

本 skill 的核心。用户已经知道数据大致怎么流,这一步用代码逐条核销,并**把代码里有而用户没提的部分挖出来**。

## 四象限

对账结果只能落进这四类之一。逐条核销 `business_map.md` 里编号的每条流向(F1、F2……),一条不漏。

| 类别 | 含义 | 处理 |
|---|---|---|
| **A 证实** | 用户断言,代码支持 | 补细节:触发条件、字段级映射、时机 |
| **B 证伪/不符** | 用户断言,代码显示不同 | **两边都记录,不判定谁对** |
| **C 代码有、用户没提** | 用户地图里没有的流向 | **本次梳理最大产出**,给足篇幅 |
| **D 用户提了、代码找不到** | 断言在代码里无痕迹 | 先怀疑锚点漏了,再考虑在系统外 |

C 类是整件事的意义所在。用户已知的部分写成文档只是记录;C 类是"不知道自己不知道"的部分,一旦某个人离职就彻底失传。

## 怎么找证据

**共现是起点,不是结论。** `probe.json` 的 `cooccurrence` 给出哪两个业务对象在同一批文件里出现——这是关系的候选,但**只证明有关系,不证明方向**。

方向要靠语义判定:

| 证据类型 | 说明 | 强度 |
|---|---|---|
| 外键 / 关联字段 | B 表存 A 的主键 → A 先于 B | 强 |
| SQL 中的读写方向 | 读 A 写 B → A 流向 B | 强 |
| 编排文件的连线 | `<transition from to>` 直接给出顺序 | 强 |
| 同段代码内赋值 | `b.setXxx(a.getXxx())` → 字段级流向 | 强 |
| 状态流转的前后置 | A 到某状态才允许 B 发生 | 中 |
| 仅共现 | 只能说明相关 | **弱,不能单独定论** |

**字段级映射比对象级更有价值。** 用户通常只知道"批次会带到光罩订单",而代码能告诉你具体带哪几个字段、哪些字段会被覆盖、哪些是快照哪些是引用。这个粒度差正是文档能提供的增量。

## 找 C 类的方法

C 类不会自己冒出来,要主动扫:

1. **看 cooccurrence 里用户没提过的高分组合** —— 两个对象频繁同处一文件却不在用户地图里,大概率有未知关系
2. **看反向流** —— 用户说 A → B,代码里有没有 B → A?回写、回滚、状态倒退很常见,而且几乎没人主动提
3. **看定时任务触发的流转** —— 界面上看不到的自动流转
4. **看绕过路径** —— 管理员直接改状态的入口、`FORCE`/`ADMIN`/`SKIP` 之类的分支。这类口子的存在意味着正常流程在某些场景下不够用,背后一定有故事
5. **看外部系统写入** —— 有没有别的系统直接改本系统的表

第 4 项特别值得挖。它同时是重构风险点、合规风险点和一段流程史。

## D 类的处理顺序

**先怀疑自己,再怀疑用户。** 顺序不能反:

1. 锚点别名漏了 → 补别名重跑一次 probe(这是允许的第二次调用)
2. 这段逻辑在编排 XML 或 JSP 里,常规搜索方式没覆盖到 → 针对性查
3. 确实不在本系统 → 在别的系统 / 手工流程 / 已废弃

三种情况含义完全不同。跳过前两步直接下"代码里没有"的结论,是这一步最容易犯的错。

## B 类的纪律

代码和用户说法冲突时,**不要擅自判定谁对**。三种可能:

- 代码有 bug(用户的认知是正确的业务需求)
- 用户记错了或记的是旧版本
- 某次变更后没人同步认知

处理方式完全不同,必须交回用户。产出里两边并列陈述,标明各自证据:

> **F7 · 批次作废后光罩订单自动取消** — [B 不符]
> 你的描述:批次作废时关联的光罩订单会自动取消。
> 代码显示:`BatchBiz.java:412` 作废批次时只更新了 `TO_BATCH.STATUS`,未见对 `MASK_ORDER` 的任何写入;全库未搜到批次作废触发订单取消的路径。
> **可能是:功能缺失 / 由人工处理 / 在别的系统完成。请确认。**
