# EOS 7 平台背景:业务逻辑到底藏在哪里

首次执行本 skill 前必读。这份文档解释了为什么常规的"读 Java 代码"方法在 EOS 系统上会失效。

## 核心事实

普元 EOS(Primeton EOS)是构件化开发平台。它的**业务逻辑主体不写在 Java 里,而是以 XML 形式存储的可视化编排**。开发者在 IDE 里拖拽节点画流程,平台把流程序列化成 XML,运行时由引擎解释执行。

这意味着:

- Java 文件里大量是**薄胶水层**——生成的构件接口、DAO 骨架、工具类。只读 Java 会得出"这系统没什么业务逻辑"的错误结论。
- 真正的分支判断、循环、赋值、构件调用顺序,都在**编排 XML** 里。
- 另一部分逻辑散落在 **JSP scriptlet**(`<% ... %>`)中。前后端不分离 + JDK 1.6 时代的项目,JSP 里塞业务判断是常态,这些代码从不出现在任何 Java 分析工具的视野里。

**结论:XML 编排文件和 JSP 是一等公民,Java 是二等。**

## EOS 概念到通用概念的映射

| EOS 概念 | 大致等价于 | 梳理时的价值 |
|---|---|---|
| 构件包 (Component Package) | 模块 / 包 | 模块边界,通常按业务域划分 |
| 运算逻辑构件 | 业务方法 / Service 方法 | **业务逻辑主体所在** |
| 数据实体构件 | Entity / ORM 映射 | 表结构 + 字段业务含义 |
| 页面流 | Controller 路由 | 页面跳转 = 业务节点序列 |
| 数据字典 / 数据元 | 枚举 + 值域定义 | **术语表金矿,常带中文名** |
| BPS 流程定义 | 工作流 | 审批链、办理人、节点 |
| 展现构件 / EOS 标签库 | 视图层 | JSP 里的业务判断 |

## 需要实测确认的文件类型

不同 EOS 版本、不同项目的扩展名和目录约定有差异。**以下是候选清单,不是事实**。S0 必须用 `probe.py --recon` 实测统计,以实际结果为准。

编排/逻辑定义(优先级最高):
- `.logic` / `.bizlogic` / `.biz` —— 运算逻辑构件
- `.cmpt` / `component.xml` —— 构件包描述
- `.flow` / `.pageflow` —— 页面流
- `.bpmn` / `.wf` / `.xpdl` —— BPS 流程定义

数据定义:
- `.dao` / `.entity` / `*-mapping.xml` / `*Mapper.xml` —— 实体与 SQL
- `.dict` / 字典表(常见表名含 `DICT`、`CODE`、`TYPE`)

配置:
- `application.xml`、`eos-*.xml`、`*-config.xml`、`web.xml`
- `.properties`(数据源、外部系统地址、开关)

**S0 的一项硬性任务:找出本项目中承载编排逻辑的实际扩展名,写进 `00_repo_map.md`,后续所有步骤以此为准。**

判据看 `recon.json` 的 `ORCHESTRATION_CANDIDATES`:带坐标属性(`x=`/`y=`)的文件几乎必然是可视化编排产物——只有图形编辑器才会存坐标。

判断方法:找一个体积较大的 XML 文件打开看,如果内容是节点/连线/条件表达式的结构(通常有 `<operation>`、`<node>`、`<transition>`、`<condition>` 之类的标签,或坐标属性 `x=` `y=`),那就是编排文件。带坐标属性是很可靠的信号——只有可视化编辑器才会存坐标。

## JDK 1.6 时代的特征

这些特征影响提取策略:

- **没有 `enum` 或很少用** —— 常量多半是 `public static final String STATUS_XXX = "03";`。只找 `enum` 关键字会几乎一无所获,必须同时看 `probe.py` 输出的 `constants` 和 `sql_write` 命中。
- **魔法数字/字符串遍地** —— `if ("03".equals(status))` 这种写法很常见。反过来这是好事:把所有字面量按出现频次排序,高频短字符串就是状态码候选。
- **没有注解式配置** —— 一切在 XML 里,所以 XML 覆盖率决定梳理质量。
- **中文注释和中文常量名可能是 GBK/GB18030 编码** —— 读文件前先探测编码,乱码会让术语表全废。`recon.sh` 会做编码抽样。

## JSP 的特殊处理

JSP 里值得提取的:

- `<% %>` scriptlet 中的 `if` 判断 —— 常含权限控制和状态可见性规则("哪个角色在哪个状态能看到哪个按钮"),这是业务规则的重要来源,且几乎不会出现在 Java 里。
- 表单字段 `name` 属性 —— 对应实体字段,是术语表的补充来源。
- 按钮/链接文案 —— **最人话的业务语言**,因为受众是业务方。`probe.py` 的 `per_anchor.messages` 会抓这些。
- 提交目标 URL —— 页面到后端动作的映射。

## 常见陷阱

- **构件名是拼音缩写** —— `LptWlDy`、`GdsSbGl` 这类。别猜,去看它调用了哪些表、抛了什么错误文案,用行为反推含义。
- **同一业务概念多套命名** —— 系统演进留下的,比如 `mask_order` / `gb_order` / `guangzhao_dd` 指同一件事。锚点文件要把它们**归到同一个业务名下**(S1),否则同一业务会被拆成几条互不相干的线。
- **XML 里的表达式语言** —— 编排文件的条件分支常用平台自有的表达式语法,不是标准 Java。不确定语义时标 `inferred` 并注明原文,别硬解释。
- **生成代码混在手写代码里** —— 带 "generated"、"由工具生成,请勿修改" 注释头的文件,业务价值低,可降权处理但不要完全忽略(生成器的输入配置反而有价值)。
