# S2 — 逐业务对象取证

对每个锚点,把 probe 定位到的证据展开成四件事:**状态、规则、入口、产物**。

这是唯一大量读代码的环节。但读的是 probe 已定位的具体位置,不是遍历目录——`per_anchor.evidence_by_kind` 里每条都带 `路径:行号`,按需打开即可。

## 处理顺序

按 `total_hits` 从高到低,先做用户业务地图里的核心对象。`top_files` 里 `stale_days` 小的优先——仍在改动的大概率是活代码。

不必对每个锚点都做到同样深度。用户在 S0 说的文档受众决定深度:onboarding 用途做到状态 + 入口即可;要重构就必须把规则和边界条件挖穿。

## 一、状态取值与流转

probe 的 `constants` 给了状态常量候选。但 **JDK 1.6 的现实是很多状态值没有常量名**,直接写成 `if ("03".equals(status))`。

从 `evidence_by_kind` 里这几类找:

- `const_def` —— 有名字的状态值
- `sql_write` —— `UPDATE ... SET xxx_status = '05'`,这是流转的直接证据
- `field_write` —— `.setXxxStatus(...)`
- `conditions` —— 前置判断,给出流转的约束

**关键:光有状态取值集合推不出流转,必须找写入点。** 每个写入点记录五要素:

| 要素 | 从哪拿 |
|---|---|
| 目标状态 | 赋值的字面量或常量 |
| 前置状态 | 同段逻辑的前置判断 / SQL 的 WHERE |
| 触发动作 | 所在方法 + 调用它的页面或编排节点 |
| 前置校验 | 同段的 if / 抛错分支 |
| 证据 | `路径:行号` |

**前置状态经常拿不到**——老代码常直接改状态不做判断。标 `前置状态: 未约束` 并单独列一节。这本身是重要发现:说明流程约束靠人工纪律而非系统保障,是重构风险点,也是用户一定有话说的话题。

给每个状态值找中文含义,来源优先级:字典表 → 错误/提示文案(`messages`)→ JSP 显示文本 → 常量名。找不到标 `unknown`,不要编。

## 二、业务规则

`per_anchor.messages` 是规则的第一来源。一行 `throw new BizException("DRC未签核,不能提交光罩订单")` 同时给出两个业务概念和它们的顺序约束——比十行注释都有用,因为它是开发者当时真实业务理解的直接记录。

**每条文案必须回到 evidence 位置读触发条件。** 文案给业务含义,条件给精确规则,两者必须配对:只有文案没有条件,规则是模糊的;只有条件没有文案,不知道它在管什么业务。

规则写成「什么条件 / 什么被禁止或要求 / 违反时发生什么」:

- ✅ 「批次状态为 `03` 且 `SIGNOFF_FLAG != 'Y'` 时,提交光罩订单被拒绝,提示"DRC未签核…"。证据: `MaskOrderBiz.java:213`」
- ❌ 「系统会校验签核状态以确保数据质量」——泛化到没有信息量,且"确保数据质量"是代码里没有的目的推断

**规则的「为什么」几乎永远不在代码里。** 想写为什么就停下,变成一个问题放进待确认清单。「为什么 X 必须先于 Y」正是用户和老员工最能讲、最有沉淀价值的东西。

## 三、操作入口与角色

从 `evidence_by_kind` 的 JSP/编排命中里找:

- **JSP 里的 `<% if %>` 权限判断** —— 前后端不分离的系统里,「谁在什么状态下能看到什么按钮」几乎全在这里,而且从不出现在任何 Java 分析结果中。**这是权限模型的真实形态,别漏。**
- **按钮/链接文案** —— 直接就是业务动作名,是全代码库最人话的地方
- **编排文件的节点名** —— 可视化编排的节点名通常是开发者手写的中文,可读性远高于 Java 方法名

产出应能回答:这条业务线上有哪些角色,各自管哪一段。

## 四、数据产物与外部交互

tape out 系统的核心交付物往往是文件。找文件读写、上传下载、目录配置项。

对每个文件类型记录:谁产生、格式、存哪、谁消费、**命名规则**。命名规则尤其重要——半导体的文件名通常编码了产品、版本、层次、工艺信息,解析命名规则的那段代码等于一份免费的数据字典。

同时记录外部系统调用(HTTP/WebService/FTP/MQ/第二数据源)和定时任务。定时任务里的自动流转是最容易失传的知识:界面上看不到,用户也常常只知道"它会自己变"。

**外部系统的用途是幻觉高发区。** 看到 IP 和端口不要猜对面是什么系统。能确定的只有"本系统向 `10.x.x.x:8080/xxx` 发送含 A/B/C 字段的请求";对面是什么,除非配置项名或注释明说,否则标 `unknown` 进待确认。这类问题问用户成本极低、收益极高——他们一看 IP 就知道。

## 产物结构

每个业务对象一节,汇成 `01_objects.md`:

```markdown
## 业务对象:<名称>
- **代码标识**: 表 / 类 / 构件
- **在用户地图中的职责**: [U]
- **状态取值**
  | 值 | 常量名 | 业务含义 | 含义来源 | 置信度 |
- **状态流转**
  | 从 | 到 | 触发动作 | 前置校验 | 入口 | 证据 | 置信度 |
- **无前置约束的写入点** ← 风险清单
- **业务规则**
  | # | 条件 | 约束 | 提示 | 证据 | 置信度 |
- **操作入口与角色**
- **数据产物 / 外部交互**
- **与用户描述不符之处** ← 交给 S3
```

最后一栏是 S3 的输入,取证过程中随手记,不要等到 S3 再回想。
