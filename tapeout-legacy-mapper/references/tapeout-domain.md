# 半导体 Tape Out 领域骨架(待验证假设)

## 使用纪律 —— 先读这一段

这份文档里的内容是**行业通用认知,不是本系统的事实**。它的唯一合法用途是:

1. 提供一个骨架,让你把代码里发现的东西**对号入座**
2. 提供术语候选,帮助识别代码里的拼音缩写和内部黑话
3. **发现差异** —— 对不上的地方才是最有价值的产出

**禁止用法**:在没有代码证据的情况下,用这里的术语描述本系统的行为;或者把这里的流程顺序当作本系统的流程顺序写进产物。

每个企业的 tape out 流程都有大量自有约定,不同工艺节点、不同 foundry、不同产品类型的流程差异也很大。**代码永远优先于本文档。**

## 典型流程骨架

粗粒度阶段(实际系统可能只覆盖其中一段):

**设计侧**
1. 设计完成 / 设计冻结(design freeze)
2. 物理验证与签核(signoff)—— DRC、LVS、ERC、Antenna、DFM 等检查项;不通过的项可能走豁免(waiver)审批
3. 数据交付准备 —— 生成版图数据(GDSII / OASIS)、层次映射(layer map)、版本冻结

**交接**
4. Tape out release —— 数据正式发布/提交,通常有多方会签
5. 向 foundry 或 mask house 提交数据

**制造侧**
6. 掩模数据准备(MDP)—— fracturing、OPC/RET 等数据处理,产出 jobdeck
7. 光罩订单(mask order)—— 下单、报价、排期
8. 光罩制造与检测 —— 写入、检查、必要时修补
9. Wafer start / fab in —— 投片

**变更与迭代**
- ECO(工程变更)可能触发部分回退与重新签核
- Respin / 版本迭代
- MPW / shuttle(多项目晶圆)与 full mask set 的流程往往不同

## 常见的流程约束模式

这些是**常见模式**,用来提示你去代码里找对应的规则,不是本系统的规则:

- 数据版本与 PDK 版本必须匹配
- 所有检查项签核完成(或有已批准豁免)才能发布
- 发布后数据冻结,变更需走 ECO
- 光罩订单需要确定的数据版本 + layer map + jobdeck 齐备
- 不同工艺节点/foundry 走不同的检查项集合和审批链
- MPW 有 shuttle 排期窗口的硬时间约束

## 差异记录要求

S4 合成时,对用户地图未覆盖的环节记录三类差异:

| 差异性质 | 含义 | 处理 |
|---|---|---|
| 标准有、本系统无 | 可能在其他系统 / 本公司不做 / 手工流程 | 进 06 确认 |
| 本系统有、标准无 | **最有价值**,企业特有流程 | 重点描述,进 06 问背景 |
| 顺序或粒度不同 | 可能反映特殊组织分工 | 高优先级确认 |

第二类要特别珍惜:它往往对应着某年某个事故之后加的管控、某个大客户的特殊要求、或者本公司独有的产品形态。这类知识一旦老员工离职就彻底失传,是整个梳理项目最该抢救的部分。
