# Tapeout Legacy Mapper

在用户已有业务认知的基础上,用代码取证、补细节、找差异,产出可维护的流程沉淀。

## 核心前提:用户的业务地图是起点,不是终点

本 skill 假设用户**已经知道核心业务对象和大致数据流向**。这改变了整个方法论:

- 不需要从零发现业务 —— 用户的地图就是骨架
- 工作重心从「找出流程是什么」变成「**用代码验证流程,并找出代码与认知不一致的地方**」

**不一致的地方就是全部价值所在。** 用户已经知道的东西,写成文档只是记录;而代码里有、用户认知里没有的东西——某个绕过校验的口子、某条从没人提过的自动流转、某个和主流程顺序相反的分支——才是真正的知识空洞,是"不知道自己不知道"的部分。

所以每一步都要问:**代码在这里说了什么用户没说的话?**

## 三条铁律

**铁律一:无证据不结论。** 每条业务结论必须附 `路径:行号` 或表名字段名。无法从代码读出的只能进待确认清单,不得进正文。

**铁律二:禁止由命名推断行为。** 函数名、表名、构件名只是**线索**,不是**证据**。EOS 系统里大量构件名是拼音缩写或历史遗留,望文生义错误率极高。`probe.py` 输出的 `hit_kinds` 分类同样是启发式线索,采信前必须打开原位置确认。

**铁律三:用户的业务地图是高置信假设,不是免检结论。** 它优先于任何行业常识,但仍需代码印证。代码与地图冲突时,**两边都记录,不要擅自判定谁对**——可能是代码有 bug,可能是用户记错,也可能是某次变更后没人同步认知。这三种情况的处理方式完全不同,必须交回用户判断。

置信度标注:`[C] confirmed`(读过实现)/ `[I] inferred`(多处间接证据,须注明推断链)/ `[G] guessed`(仅命名线索,**不进正文**)/ `[U] user-asserted`(用户提供,代码未印证)。

## 执行流程

四步。整个项目只需 **2~3 次脚本调用**。

### S0 · 交底与测绘

先拿用户的业务地图。**不要跳过这一步去猜**——这份地图决定后面所有工作的靶心。具体怎么问、要问到什么颗粒度,读 `references/intake.md`。

同时跑一次仓库测绘:

```bash
python3 scripts/probe.py <代码库根> --recon --out <输出>/_raw/recon.json
```

从 recon 结果里必须敲定三件事,写进 `00_repo_map.md`:

1. **编排文件的实际扩展名** —— 看 `ORCHESTRATION_CANDIDATES`,带坐标属性的文件几乎必然是 EOS 可视化编排产物。抽样打开 `samples` 里的文件确认。
2. **文件编码** —— 看 `ENCODING_WARNING`。是 GBK 就立刻记录,后续所有读取显式指定编码,否则中文术语全部作废,而且失败很隐蔽。
3. **模块布局与疑似死区** —— `component_package_dirs`、`suspected_dead_dirs`、`staleness_by_dir`。

首次执行还必须读 `references/eos7-primer.md`。它解释了 EOS 的业务逻辑**不在 Java 里而在编排 XML 和 JSP 里**——不读它会把整个梳理方向做反。

### S1 · 锚点化

把用户的业务地图翻译成锚点文件(格式见 `references/intake.md`),然后一次跑完:

```bash
python3 scripts/probe.py <代码库根> --anchors anchors.txt --out <输出>/_raw/probe.json
```

**别名宁滥勿缺。** 命中噪音可以人工剔除,漏了就整条业务线断在这里。每个业务对象至少给:中文名可能的拼音缩写、疑似表名、疑似字段前缀、疑似 Java 类名。

拿到结果先看 `ZERO_HIT_ANCHORS`。命中为零有两种截然不同的含义——**别名给错了** vs **该业务不在本系统实现**。把它当成"系统没这功能"是典型误判。区分方法:换一批别名重试一次;仍为零再考虑第二种可能,并作为高优先级问题记录。

允许在这里跑第二次 probe(补别名),但控制在两次以内。

### S2 · 逐业务对象取证

对每个锚点,从 `per_anchor` 的证据出发,补齐四件事:状态取值与流转、业务规则、操作入口与角色、数据产物。

详细指令读 `references/s2-evidence.md`。这一步会实际打开文件读代码,是整个流程里唯一大量读代码的环节——但读的是 probe 已经定位好的具体位置,不是遍历。

### S3 · 数据流对账 ← 本 skill 的核心

拿用户断言的每一条数据流向,去代码里找证据,产出**对账表**:证实 / 证伪 / 代码里有但用户没提 / 用户提了但代码里找不到。

详细指令读 `references/s3-dataflow.md`。第三类和第四类是本次梳理的主要产出,要给足篇幅。

### S4 · 合成与缺口

以用户的业务地图为骨架,把 S2/S3 的取证结果挂上去,产出主流程文档和待确认清单。

详细指令读 `references/s4-synthesis.md`。

**S4 不再读代码**,只用 S0~S3 的产物。拼不上的地方写「流程断裂」,不要补圆——补出来的连接是纯编造,而且因为出现在成品显眼处,危害远大于中间产物里的一条错误记录。

## 唯一的脚本

`scripts/probe.py`,两种模式,纯标准库,不依赖 git 和网络。

```bash
python3 scripts/probe.py --help          # 查看完整用法
python3 scripts/probe.py <root> --recon --out r.json
python3 scripts/probe.py <root> --anchors anchors.txt --out p.json
```

设计上把机械提取压缩成一两次遍历。**能从 probe 输出读到的,不要再去翻文件**;需要确认具体行为时,才按 evidence 定位打开。

没有 git 的替代方案:优先级判断用**文件 mtime**(`staleness_by_dir`、`top_files[].stale_days`)和**引用计数**(`total_hits`、`cooccurrence`)。长期未改动 + 低引用 = 死代码线索,但仅是线索——静态分析无法确认废弃,需要运行时数据佐证,这一点要向用户说明。

## 输出规范

产物模板与格式见 `references/output-templates.md`,首次产出前读它。

半导体术语骨架在 `references/tapeout-domain.md`,**仅在用户地图未覆盖的部分作为术语候选使用**,且严格禁止用行业常识填补代码证据的空白。用户的地图永远优先于这份通用材料。

## 收尾时要告知用户的

- 这份文档的定位是覆盖已知主线 + 标出代码与认知的差异,不是完整百科
- 死代码判断、真实数据追踪需要运行时数据和生产库权限,不在本 skill 范围
- S3 的「代码里有但你没提」清单是最该优先过一遍的部分
