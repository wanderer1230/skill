AI研发提效 · 业务理解与安全变更
CodeGraph + Business Knowledge + OpenSpec + DeepSeek
AI CHANGE ENGINEERING

AI理解了代码以后，如何理解业务并安全完成一次变更？

核心不是让模型“猜业务”，而是把代码事实、业务事实、历史事实和变更意图组合成可审查的上下文， 形成“业务理解 → 影响分析 → 变更契约 → 受控实施 → 独立验证 → 知识回流”的闭环。

一句话架构
CodeGraph 解决“代码怎么连接”，Business Knowledge 解决“业务为什么这么做”，OpenSpec 解决“这次要改变什么”，Verifier 证明“实际改动没有超出业务意图”。
核心原则
AI先理解，再计划；先形成变更契约，再修改；先验证，再交付；未知业务规则不能由AI自行决定。

01 · 四层事实模型

业务理解不是单一知识库
Code Fact
CodeGraph：调用、依赖、模块、测试、事件、影响面
Business Fact
术语、规则、流程、状态机、业务不变量、模块职责
Historical Fact
Git / PR / 历史需求 / ADR / 过去类似改动
Change Fact
本次需求、Scope、Spec、Acceptance、风险、约束
AI 的业务理解 = 多源事实的组合，而不是“读一份业务文档”。
每个业务结论都应尽可能带 Evidence；无法确认的内容明确标记 UNKNOWN，不允许模型把推测升级成业务事实。

BusinessTerm

订单、支付成功、取消、结算等业务概念，以及代码名称、数据库名称、历史叫法。

BusinessRule / Invariant

“什么情况下允许做什么”“什么情况绝对不能发生”，是安全变更最重要的约束。

BusinessFlow / StateMachine

业务路径、异常路径、状态转换及跨模块动作，让AI理解行为而不只是理解类。

rule: "普通订单30分钟未支付自动取消"
status: CONFIRMED
source: ["product_requirement", "OrderTimeoutJob", "OrderTimeoutTest"]
confidence: HIGH
evidence: ["OrderTimeoutJob.java:120", "OrderTimeoutTest.java:85"]

03 · FACT / INFERENCE / UNKNOWN

防止AI把“代码现在这样”误当成“业务规定就是这样”

FACT事实

有代码、需求、测试、文档等直接证据支持的内容。

例如：OrderTimeoutJob 每5分钟执行一次。

INFERENCE推导

基于多个事实得出的合理结论，但不是业务原文。

例如：实际取消时间可能存在0~5分钟延迟。

UNKNOWN未知

现有资料不足以确认，必须进入 Open Question。

例如：业务是否接受最大5分钟的延迟。

05 · OpenSpec：把业务意图变成“变更契约”

不是告诉AI改哪一行，而是规定系统改完以后应该表现成什么样

业务层

背景、目标、Scope、Business Rules、Scenario、Open Questions。
核心：描述“应该发生什么”，而不是先决定“代码怎么写”。

技术层

Impact、Technical Design、Tasks、Acceptance、Risk。
核心：让设计和实现受到明确边界约束，并可被自动验证。
## Requirement: Order Timeout

The system SHALL cancel an unpaid normal order after 20 minutes.

### Scenario: Normal order timeout
GIVEN a normal unpaid order
WHEN 20 minutes have elapsed
THEN the order becomes CANCELLED
AND inventory is released
AND OrderCancelledEvent is published

06 · Change Contract：AI修改代码前的安全边界

把“允许改什么、不能改什么、改完要满足什么”结构化
change: change-order-timeout

intent: "普通订单取消时间从30分钟改为20分钟"

scope:
include: [Order, OrderConfig]
exclude: [VIP, PromotionOrder, PaymentSuccess]

business_rules: [BR-001, BR-002, BR-003]
expected_impact:
modules: [Order, Inventory]
events: [OrderCancelledEvent]

acceptance: [AC-001, AC-002, AC-003]
risk: [concurrent_cancel, existing_orders]
安全机制：Builder 无权自行扩大 Scope；发现新的业务规则或冲突时必须回到 Open Question / Spec，而不是自行决定。

07 · Builder：受控实施，而不是自由发挥

先拿完整 Change Package，再允许修改
Change Package
Business Understanding业务事实 / 规则
OpenSpec需求 / Scenario / Scope
CodeGraph ContextEdit Context / Impact
Relevant Tests现有验证
HistoryGit / PR
↓
DeepSeek + OpenCode BuilderPlan → Edit → Test → Fix → Test

允许

修改批准范围内代码、补测试、执行构建和测试、生成变更说明。

禁止

自行修改业务规则、扩大Scope、直接进行高风险生产操作。

异常处理

发现新的影响或业务冲突 → STOP → 生成Open Question → 回到Spec。

08 · Verifier：三层验证

不能只做“代码Review”，必须验证业务契约
层次检查什么核心证据
代码验证编译、单测、集成测试、静态检查、异常路径Build / Test / Lint
Spec验证每个 Requirement、Scenario、Acceptance 是否实现OpenSpec + Test Result
业务回归验证实际影响是否超出预期，是否引入未声明的模块/接口/事件变化CodeGraph + Git Diff + Business KB
关键控制： Expected Impact 与 Actual Changed Impact 必须对比。 如果 Spec 声明只修改 Order / Config，但 Git Diff 出现 Payment / Settlement 等非预期模块，Verifier 直接阻断。

10 · 这套体系为什么能持续提效

每一次真实变更都在增加下一次任务的上下文质量

第一次

AI需要大量查询CodeGraph、Git和业务资料，人工确认业务事实。

第二次

同类业务规则已经进入Business Knowledge和历史Memory，AI更快定位与判断。

长期

业务知识、CodeGraph事实、历史决策、Spec和验证结果形成持续增长的研发知识资产。

最终形成知识飞轮： 代码变化 → 识别新知识 → 人工确认 → 进入知识层 → 下一次任务上下文更完整 → 研发进一步提效。

11 · 向领导汇报的核心结论

技术方案最终落脚在“安全完成一次业务变更”

不是让AI直接改代码，而是建立一条可验证的AI变更链：

业务理解 → 影响分析 → 变更契约 → 受控实施 → 独立验证 → 知识回流

一句话： CodeGraph 负责代码世界，Business Knowledge 负责业务世界，OpenSpec 负责变更契约，DeepSeek 负责综合推理，Verifier 负责证明“改动符合业务意图且没有越界”。
