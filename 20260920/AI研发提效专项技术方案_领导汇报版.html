AI NATIVE ENGINEERING

以 AI 重构大型业务系统研发方式

基于现有内网能力，建设“模型 + Agent + Tools + Knowledge + Governance”的研发智能层。 目标不是单纯让 AI 多写代码，而是让 AI 参与需求理解、系统分析、影响评估、编码、测试、Review 与知识沉淀。

200%+
挑战目标：单位研发资源下的有效交付能力提升；以试点数据验证，不把 200% 作为未经验证的承诺。
1 → 4
先从一个核心业务域试点，再复制到主要业务模块，避免一开始做“大而全平台”。

01 · 核心判断

先解决大型系统最昂贵的“上下文成本”
关键问题不是 AI 会不会写代码，而是 AI 能不能正确理解“这个需求在整个系统里意味着什么”。
当前主要成本集中在：业务理解、代码定位、调用链分析、影响面判断、历史逻辑追溯、测试和 Review，以及业务知识依赖个人经验。
业务理解
规则、流程、术语分散在代码和个人经验中
系统导航
模块多、关联强，定位影响范围耗时
重复劳动
代码、测试、文档、Review存在大量可自动化工作
知识流失
需求完成后知识没有自动回流到组织资产

03 · 知识如何进入模型

核心技术：Context Engineering，而不是第一阶段就做训练
原则：模型负责推理，知识层负责提供企业私有上下文，Agent 负责动态取数与执行。
第一阶段不建议把业务知识 Fine-tune 进 DeepSeek。业务频繁变化时，外部知识层更容易更新、审查、回滚和复用。
用户需求自然语言任务
→
Task Analyzer识别任务类型
→
Retrieval知识 + 代码 + 图
→
Context Builder组装相关上下文
→
DeepSeek推理 / 生成

业务知识检索

从 Business Glossary、业务流程、规则、模块卡片中找到与任务相关的知识。

代码与结构检索

结合关键词搜索、符号搜索、AST、调用图、依赖图、Git历史等方式形成系统上下文。

动态 Tool Calling

模型发现上下文不足时主动调用工具，例如查调用方、数据库、MQ、测试和历史变更。

推荐的检索组合：关键词 + 语义 + 结构关系（Hybrid Retrieval）。
第一阶段可以先用 Git、代码搜索和 Markdown 知识跑通；后续再引入 Embedding / Reranker / Vector DB / Knowledge Graph。

06 · 业务知识如何持续沉淀

形成“代码变化 → 知识变化 → AI越来越懂系统”的飞轮
Git Diff识别变更
→
Knowledge Agent判断知识影响
→
Candidate生成知识提案
→
Human Review确认事实
→
Confirmed进入知识库

UNKNOWN

AI不知道、或者只有推测的信息。不能直接进入正式业务知识。

CANDIDATE

AI从代码、需求、Git历史等发现的候选事实，等待验证。

CONFIRMED

有需求、代码、测试或人工确认依据的正式知识，可被后续任务复用。

07 · 第一阶段 MVP

不做大而全平台，先跑通一个真实业务闭环

第一阶段建设

① 一个核心业务域的 System Overview、Business Glossary、Business Flow、Module Card； ② Code Search；③ Trace / Dependency；④ Scout / Architect / Builder / Verifier； ⑤ OpenSpec流程；⑥ Knowledge Update。

第一阶段验收标准

用真实历史需求验证：AI能否找到正确代码、正确影响范围、形成可执行Spec、完成代码与测试，并经过Verifier验证；所有结果可追踪、可审查、可回滚。

09 · 效果怎么证明

建立历史需求 Benchmark，而不是只看“AI写了多少代码”
Lead Time
单需求端到端耗时
Impact Recall
实际受影响范围被AI识别的比例
First Pass
一次实现通过率 / Review返工率
Regression
回归缺陷 / 线上问题变化
建议建立 50～100 个历史真实需求作为 Benchmark。
同时对比人工方式与AI辅助方式的分析耗时、编码耗时、Review返工、影响分析召回率、测试覆盖和缺陷情况。200%+作为专项挑战目标，以实测结果逐步验证。

10 · 风险与治理

越深入代码，越需要可控的 Agent 权限

主要风险

业务幻觉、上下文错误、误改代码、知识污染、生产风险、权限越界、质量不可量化。

治理原则

Read Only → Analysis → Spec → Approval → Modify → Test → Review；工具白名单、最小权限、操作留痕、Git Diff、人工审批和可回滚机制。

11 · 需要管理层支持的事项

把“试验工具”升级成“研发能力建设”

试点范围

明确一个核心业务域，允许以真实需求作为AI研发试点。

协同机制

允许研发、业务、架构共同确认关键业务知识，形成组织级知识资产。

数据与指标

建立历史需求Benchmark和统一指标，持续评估AI真实收益与质量影响。

建议最终定位： 不是“推广一个AI工具”，而是基于现有内网模型和研发工具，建设企业自己的 AI Native 研发基础设施。
